# Chalk 진입점 — 웹인가 앱인가

> **질문**: 강사가 브라우저에서 수업을 만들고 데스크톱 앱에서 리허설하는 지금 구조를 유지할 것인가.

## 0. ⭐ 답의 성격이 예상과 다르다

> [!key-insight] 결정을 뒤집는 일이 아니라, 비어 있는 결정을 처음 채우는 일이다
> **제품 정의 문서는 Chalk의 실행 환경을 정한 적이 없다.** "브라우저"도 "데스크톱 앱"도 제품 정의에 없다.
> 웹/앱 이원 구조는 **요구사항 층(`ARC-02`)에서 처음 등장**하고, 그 층은 lab이 아니라 **studio 소유**다.
> 즉 **왕복은 버그가 아니라 현재 요구사항이 규정한 구조**이며, 동시에 **제품 정의가 그것을 승인한 기록은 없다.**

| 문서 | 환경 서술 |
|---|---|
| `PRODUCT-LINEUP.md` | repo 열 = **"미정 (Studio 내 탑재 가능 — Product in Product)"** |
| Chalk 제안서(2026-07-30) | *"**하네스 — 반복 작업 자동화 도구 묶음.** Chalk가 여기 들어감"* · Studio만 *"참가자 노트북에 설치되는 앱"*으로 명시 |
| 같은 문서 Jay 주석(07-31) | *"코드가 들어갈 repo는 **미정**"* — 하네스 귀속도 확정 아님 |
| `product-ip-register.md` | 제품 성격은 Decided(독립 강사 제품), **실행 환경은 아님** |
| `MISSION.md` · 회의록 8/25·8/31·9/14 | 브라우저·데스크톱·진입점 논의 **기록 없음** |

> [!contradiction] 버린 선택지의 진입 모델로 구현이 가고 있다
> `2026-08-10-positioning-reset.md`가 **"Chalk를 Studio 내 탑재로 묶는다"를 기각**했다 — 이유는 기술이 아니라 사업이다(*"라이선스를 교육자에게 따로 팔 수 없게 된다"*).
> 그런데 `ARC-02`는 **"Studio에서 Chalk로 진입"**을 전제한다. **이 둘을 조정한 기록이 없다.**

## 1. 환경이 규정된 유일한 층 — 요구사항

| ID | 원문 | 함의 |
|---|---|---|
| `ARC-01` | Chalk는 화면·전달, Service는 권한·상태·서명을 소유 | Chalk = 프런트엔드 층 |
| **`ARC-02`** | **"Studio에서 Chalk로 진입하며 인증을 URL에 넣지 않는다. 웹 진입과 내장 화면을 구분한다"** | **둘 다 있는 것이 설계 전제** |
| `DES-03` | 375/390/768/1280/1440px 반응형 | 모바일 포함 = 웹 전제 |
| `RUN-01` | 강사 전용 권한 없이 **학생 조건으로 리허설** | 학생 실행 환경 = **Studio 앱** |
| `ENV-07` | 지원 OS·아키텍처·**최소 앱 버전**·네트워크·계정 조건 명시 | 앱 버전 의존 명시 — **단 미확인** |

⚠️ `chalk-authoring`의 `WEB-01~09`는 **Chalk의 환경이 아니라 실습 과제(홈페이지 만들기)** 요구사항이다. 혼동 주의.

한편 볼트 쪽에는 반대 방향의 선언이 있다 — `CR-DEF-06`: *"저장소를 어디에 두든 **강사가 만나는 정본은 웹 화면 하나**다."* [[chalk-target-shape-proposal]]도 같은 말을 한다 — *"내장 화면은 진입 경로이고 웹 화면이 정본."*

## 2. 강사 여정 — 앱 전환 2회, 사이에 수작업

```
브라우저 (Chalk)                          Studio 앱
─────────────────────────────────────────────────────────────
/start → /authoring  저작·저장
       → /console    연습 세션 열기
       → /issuer     참여 코드 발급
                         │ ★ 코드를 손으로 복사해 옮긴다 ──► 전환 ①
                         ▼
                                    시작 화면에 코드 붙여넣기
                                    학생 조건으로 실습 (= 리허설 상당)
                         ◄─────────────────────────────── 전환 ②
/authoring 확정 → /console 개설 → /board 운영 ─ 폰으로 보면 ─► 전환 ③(선택)
```

**전환 지점은 하나뿐인데 왕복이라 2회로 센다.** 그 사이에 **참여 코드를 사람이 복사해 옮기는 수작업**이 낀다 — 자동 연결이 없다.

## 3. ⭐ 리허설은 미구현이 아니라 **미결정**이다

`rehearsal: "not_run"`은 네 곳에 박힌 **하드코딩 리터럴**이고, 리허설을 시작·기록·판정하는 코드가 없다. **Chalk 화면에 리허설 버튼도 없다** — "리허설하세요"라는 안내 문구만 세 군데 있다. **시키는 말은 있고 시킬 버튼은 없다.**

그런데 더 중요한 것은 **어디서 돌아야 하는지를 문서가 갈라 말한다**는 것이다.

| 근거 | 가리키는 곳 |
|---|---|
| `learning-agent-experience.md:398` 레이어 배정표 — *"Surface \| … **학생 조건 리허설** … \| Chalk authoring/board/classroom"* | **Chalk (브라우저)** |
| 같은 문서 `:328` — *"학생 권한의 **독립 프로젝트**로 리허설한다. **강사의 로그인·로컬 도구가 성공을 대신하지 않는다**"* | **Studio 앱** |
| `AE-11` — *"…**앱/SDK 호환 범위**에 증거를 귀속한다"* | **앱 증거 필요** |
| `chalk/src/ui/start.html` §3 — *"Studio 설치 파일을 받으세요 … 학습자 코드를 **Studio 시작 화면에 입력**"* | **Studio 앱** (강사에게 실제로 안내하는 절차) |

**배정표만 Chalk를 가리키고 나머지 셋은 Studio를 가리킨다. 그리고 배정표가 가리키는 Chalk에는 그 버튼이 없다.**

> [!key-insight] 진입점 판단과 리허설 화해는 같은 문제다
> 리허설을 **Studio에 두기로 하면** "브라우저에서 만들고 앱에서 리허설"이 확정된다.
> **Chalk에 두기로 하면** 앱 증거 요구(앱/SDK hash, 실제 도구 실행)를 **다시 써야 한다**.

그리고 **결과가 돌아올 경로가 없다** — `authoring_versions`에 증거 칸이 없고, `VER-02`("관련 변경 시 합격 무효화")를 걸 자리가 없다. **지금은 확정이 리허설을 기다리지 않는다.**

## 4. 딥링크는 가능하다 — 전송로가 이미 있다

`HypeProof/vscodium` 조사 결과(**이 세션이 직접 확인하지 않음**):

- Studio는 이미 **`hypeproof-studio://` 커스텀 스킴을 등록**한다 (macOS LaunchServices 실제 등록 확인, v0.1.56)
- VS Code의 프로토콜→창 열기 경로를 패치로 죽이지 않았다
- **코드 변경 0으로 지금 당장 되는 것**: Chalk 페이지에 `<a href="hypeproof-studio://file/…">리허설</a>`을 두면 Studio가 그 폴더를 연다 (확인 다이얼로그 1회)

**제대로 하려면 만들 것** (전부 `hypeproof-studio` repo, **vscodium은 손댈 것 없음**):
1. **수업 식별자 계약** — 지금 Studio에 "수업/코호트"를 가리키는 파라미터가 **없다**
2. **확장 UriHandler** — `registerUriHandler` 호출 0건이라 `…/open?lesson=…`은 지금 아무 일도 안 한다. **이게 정석 경로**이고, 이러면 확인 다이얼로그 설정을 건드릴 필요도 없다
3. 수업 자료의 로컬 확보 · 4. 확인 다이얼로그 정책 · 5. 신뢰 도메인 등록

## 5. 현장 조건 — 무엇이 실제 비용인가

→ 상세는 [[chalk-instructor-field-reality]]

- ⛔ **실시된 회차의 사후 현장 기록이 사실상 0건이다.** 노트북 몇 대를 썼는지, 진행표를 무엇으로 봤는지 **관찰 기록이 없다.**
- **계정·로그인·설치가 현장 최대 병목** — 문서가 `[!risk]`로 직접 선언하고, 큐시트는 세팅에 **20분(2시간의 17%)**을 배정했다. 사전 준비물은 "5분 컷"이 목표인데 큐시트는 20분을 잡았다
- **기업 사내 회차에서 업무용 랩탑을 못 쓴다** (SK) → 개인 기기 + **"One-line installer, 5분, Mac/Win"** + 백업 노트북 5대
- **모바일 조항은 라이브 보드에만 걸린다.** `chalk/README.md`: *"**Readable in two seconds**, on a phone, **while walking the room**."* **저작을 모바일로 한다는 서술은 없다** — 요구사항은 모바일 접근성을 *"유지한다"*고만 말하고 새 용도를 주지 않는다. 설계 문서가 경계를 긋는다: *"390px 캡처를 모바일 Studio 앱 지원 증거로 쓰지 않는다."*

## 6. ⛔ 가장 큰 공백 — 강사 페르소나가 없다

`docs/personas/customer-personas.ko.md`의 페르소나는 **3종뿐이고 전부 Studio 쪽**이다 — `persona-owner`(보아치과 원장) · `persona-performer`(커리큘럼 1차 타겟) · `persona-team-lead`(바이오팜 트랙).

**Chalk의 사용자(강사·교육자)에 해당하는 페르소나가 없다.** 유일한 흔적이 `pmf-loop/state.yaml`의 `educator-chalk`인데 `status: new` — **아직 조사되지 않은 후보**다. 같은 파일이 다음 사이클 과제로 적어 둔 것:

> *"Chalk 구매자를 **강사에서 원장·교육팀장으로 재정의**한다 — 강사의 자산은 대체불가능성인데 저작도구는 그것을 낮춘다"*

그리고 **제3자 강사 운영 회차는 0건**이다(`CR-GATE-09`가 검증 조건으로 요구하는 바로 그것).

## 7. 선택지 (초안)

| | 안 | 왕복 | 비고 |
|---|---|---|---|
| **A** | 웹 유지 | 2회 | 지금 구조. 요구사항과 정합 |
| **B** | Studio 안으로 (저작도 앱) | 0회 | **모바일 조항·`CR-DEF-06`과 충돌.** 2026-08-10 기각안과 같은 방향 |
| **C** | 웹 저작 + 리허설만 딥링크 | 1회 | 전송로가 이미 있다(§4) |
| **D** | Chalk가 Studio를 띄움 | 1회 | C의 변형, 방향 반대 |

각각에 붙일 것: 되돌리기 비용 · 기존 요구사항과의 관계 · 로드맵 영향 · 데모까지 가능한가.

## 8. 판단 전에 답해야 할 것

1. **`ENV-07` 미확인을 닫는다** — 앱의 존재는 요구사항이 전제하는데 **그 앱이 무엇이고 어느 OS를 지원하는지 명시한 산출물이 없다.**
2. **리허설을 어디에 둘지 정한다** (§3). 진입점 결정과 같은 문제다.
3. **강사 페르소나를 만든다** (§6). *무엇을 고르든 이 공백은 그대로 남는다 — 그것이 먼저다.*
4. 바꾸기로 하면 **`ARC-02`가 규정한 구현 계약과 충돌**하므로 studio 요구사항 쪽과 함께 움직여야 한다.
5. **실측 기회**: **10/7 치과 워크숍**(담당 [[jehyeong]], 일정 확정)에 관찰 항목을 미리 정해 두면 §5의 빈칸을 한 회차로 채울 수 있다. `CR-RUN-12`가 이미 그 방향을 요구한다 — *"구간 대기 시간은 짐작이 아니라 실제 기록에서."*
